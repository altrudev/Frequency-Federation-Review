# Federation Attribution Receipt and Status Registry v0.1

Status: PROPOSAL / NOT AN ACTIVE FEDERATION RULE

These artifacts address two separate coordination problems without creating an economic formula or a new authority layer.

## Attribution Receipt

The attribution receipt records which project artifacts are associated with one action, the role each artifact played, the evidence references supporting the association, and who attested to the statement.

It deliberately does not decide what a contribution is worth.

The v0.1 claim ceiling keeps all of the following NOT_ESTABLISHED:

- economic value;
- payment entitlement;
- causal importance;
- external execution.

A project appearing in a receipt therefore means only what the attached evidence and attestation can support. It is not a payment instruction, endorsement, completeness claim, or proof that the project was causally decisive.

A verified attestation must reference separate verification evidence. The receipt cannot promote an unverified assertion merely because it is present in the record.

## Status Registry

The registry is an index over evidence already held elsewhere. GitHub PRs, releases, signed receipts, owner confirmations, and other immutable records remain the source of truth.

The registry has four areas:

1. projects and capabilities;
2. interoperability pilots;
3. governance decisions;
4. commercial-delivery status.

The registry does not create membership. LISTED and TECHNICAL_PARTICIPANT are descriptive states only. ACTIVE_PARTICIPANT requires an explicit opt-in reference.

The public registry may not contain customer-identifying or payment information.

## Economics boundary

No revenue share, price, amount, weight, score, commission, fee, or payment-ready field is valid in either v0.1 artifact.

That is intentional. Evidence of participation should exist before an economic formula is negotiated. A later economic layer may consume attribution evidence, but it must be governed separately and cannot retroactively reinterpret earlier receipts.

## Governance boundary

These proposal artifacts do not override project-owned nodes, edge semantics, claim ceilings, trust pins, licenses, private implementations, or background IP.

Publication of the proposal is not adoption. Adoption would require the shared review process and explicit project confirmation wherever project-owned semantics are affected.
